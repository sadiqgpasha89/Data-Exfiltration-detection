Banking · Insider threat · Reference implementation

Stop data leaving the bank, and know why you stopped it.

Sentinel is a tri-layered system for detecting and stopping data exfiltration at a financial institution: a wire-speed rules layer at the edge, an anomaly-detection layer, and an investigation layer that reasons over identity, HR and change-management context and hands a human analyst a signed case file.

Honest scope. This is a working reference implementation of the design, not a deployed product. Platform integrations (Kafka, Redis, BigQuery, Vertex AI, Neutron, identity provider, Vault) are in-process stand-ins. The detection logic, decision policy, security controls and tests are real. The use case

Most of an insider-threat system's value comes down to one moment, and the decision that follows it.

A database administrator pulls 480,000 customer records at 11:45 on a Sunday night. Is it a scheduled migration, or the start of a breach?

Within seconds the platform has to decide, and then decide whether cutting that person off the network is justified. Cut off a legitimate batch job and you cause an outage. Wave through a real breach and you have a regulatory incident.

  1. Edge rules fire in under a millisecond. Card numbers, known C2 addresses, honeytoken records and random-looking payloads are caught deterministically.
  2. Anomaly models score the behaviour. Is this volume, time of day and read-to-export ratio normal for this user and role?
  3. Investigation agents gather evidence. Is there a valid change ticket for this user, at this time, for this data and destination? Is the person resigning?
  4. A decision policy returns a verdict using evidence only, never a label the sender chose, and records it in a tamper-evident ledger.
  5. A human closes the case. Containment is a dry run by default and guarded when enabled.
Who it's for

SOC analysts, security architects and anyone studying how to build insider-threat detection that can be audited.

What it detects

Bulk exports, drip exfiltration, covert channels (DNS, steganography), use of known C2 infrastructure, and access beyond a user's entitlements.

What makes it different

Verdicts rest on evidence, quality is measured rather than asserted, and every limitation is documented.

How it works

Telemetry flows through three layers. Each layer is cheaper and faster than the one after it, so only what matters reaches an analyst.

Telemetry endpoints · databases · NetFlow

POST /api/v1/evaluate/process with an API key, a validated body and load shedding.
validate and tokenize

LAYER 1 Deterministic rules at the edge target: under 1 ms

  • Exact Data Match: file hashes of proprietary assets via a Bloom filter, then an exact set check
  • Luhn-validated cards, IBAN mod-97, plausible SSNs
  • Threat-intel feeds: IPv4/IPv6 addresses, CIDR blocks, C2 domains matched on whole DNS labels
  • Zero-tolerance egress ports from database subnets
  • Honeytokens (canary records) detected with or without separators
  • Entropy and a chi-square test of the byte histogram
features from true 15 min / 1 h / 24 h windows

LAYER 2 Anomaly detection score S, escalate at S ≥ 0.65

  • Isolation Forest over eight behavioural features, calibrated so 0.5 is the edge of benign data
  • PCA bottleneck autoencoder (linear, NumPy), calibrated on its own training distribution
  • IAM entitlement scorer: shortest-path distance from user to resource, plus resignation and privileged-hop signals
  • Ensemble weights 0.35 / 0.35 / 0.30, and escalates if any single model is above 0.85
S ≥ 0.65, or a Layer 1 flag

LAYER 3 Investigation and decision

  • Three deterministic agents: triage forensics, correlation (IAM, HR, change tickets) and compliance exposure
  • Decision policy applied to the evidence. There is no language model in this layer.
  • Guarded containment: dry run by default, protected targets never touched, hourly cap

Decisions based on evidence

The category field of a telemetry event is a label chosen by whoever sent it. It is displayed and never used to make a decision.

VerdictWhen
LEGITIMATE_BULK_OPERATION A change ticket is valid for this user, at the time of the event, for this data and this destination, with no hard indicator, no departing employee, no sensitive-data or concealment finding and no extreme score.
MALICIOUS_EXFILTRATION A hard indicator (honeytoken, known C2, proprietary-file match), or score ≥ 0.85, or a departing employee with score ≥ 0.70, or an unauthorized bulk transfer with score ≥ 0.70 and two corroborating signals.
SUSPICIOUS_ANOMALY_PENDING_HITL Score ≥ 0.65, or a sensitive-data finding, or a ticket that exists but cannot be trusted alone. A human decides.
FALSE_POSITIVE Everything else that reached Layer 3.

Security model

A detection system is itself a target. These controls are built in and covered by tests.

Authentication and roles

Every route needs an API key, compared as SHA-256 digests in constant time. Roles: viewer, ingest, analyst, admin. The analyst in the ledger is the authenticated caller, not a name in the body.

Safe containment

Dry run by default. Never touches protected users or addresses, capped per hour, and targets come from the case rather than the request. Statuses are honest: APPLIED, DRY_RUN, SIMULATED, FAILED.

Tokenization

HMAC-SHA256 pseudonyms, masked hosts and sanitized SQL. Production refuses to start without a real key.

Input and abuse limits

Every field is bounded and validated. Request bodies are capped, payload scanning is bounded, and per-key rate limits (429) and concurrency limits (503) apply.

Tamper-evident audit

Append-only hash chain, written durably, verified at start-up (a tampered file stops the service), with a /readyz check.

Start-up gate

With APP_ENV=production the service refuses to start without a tokenization key, API keys, a ledger path and authentication turned on.

What is and isn't real

Real and tested

  • Validation and tokenization
  • Every Layer 1 rule
  • Feature windows and the three Layer 2 models, with calibration
  • Ticket authorization logic and the decision policy
  • Containment guard and case closure rules
  • Durable hash-chained ledger
  • Authentication, authorization, rate limiting, load shedding
  • Drift statistics (PSI, Wasserstein, KS) and the benchmark

Stand-ins

  • Kafka, Redis, BigQuery and Vertex AI are in-process and bounded
  • Containment adapters (Neutron, identity provider, Vault) report SIMULATED until real ones are registered
  • Retraining is recorded as requested until a backend is registered
  • Change-ticket signatures are not verified
  • The agents are deterministic; the prompt registry is not wired to a model

Also worth knowing: the models are fitted on a synthetic benign baseline, steganography cannot be detected reliably from file bytes alone, and the cockpit's Content-Security-Policy still allows inline scripts.

Run it yourself

Development mode (authentication off, simulator on):

git clone https://github.com/sadiqgpasha89/Data-Exfiltration-detection.git
cd Data-Exfiltration-detection
make install
make run            # http://127.0.0.1:8080

Production-shaped (authentication on, durable ledger, read-only container):

make keys           # prints a tokenization key and an admin API key
cp .env.example .env   # then edit
docker compose --env-file .env up --build

Tests: make test (180 tests, about 10 s, 95% line coverage), make test-eval, make lint, make audit.
